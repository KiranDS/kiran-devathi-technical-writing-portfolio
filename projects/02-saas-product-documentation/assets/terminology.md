# Terminology and editorial standards

**Applies to:** SupportFlow portfolio documentation  
**Version:** 1.0

## Voice and tone

Use a professional, direct, neutral, and helpful tone. Write for users who want to complete a task or understand a product concept.

## Writing principles

- Address the reader as **you** where appropriate.
- Use present tense for product behaviour.
- Use active voice when the actor is known.
- Prefer short sentences and familiar terms.
- Put the most important information first.
- Explain acronyms at first use in each standalone document.
- Avoid marketing claims, unsupported guarantees, and vague superlatives.

## Procedures

Use numbered steps for sequential tasks.

Each procedure should include:
1. A descriptive task heading.
2. Prerequisites, when necessary.
3. One action per step where practical.
4. UI labels in bold.
5. An expected result when it helps the reader verify completion.

Use **Note** for useful supplementary information and **Important** for information that prevents a significant error or misunderstanding.

## UI terminology

- Match UI labels exactly and capitalise them consistently.
- Use bold for selectable UI labels, for example, select **Queues**.
- Use quotation marks for text a user must enter only when needed.
- Do not invent UI labels for a real product. In this fictional project, labels are explicitly illustrative.

## Tables

Use tables for structured comparisons, field definitions, role matrices, and metric definitions. Do not use a table when a short list is easier to scan.

## Links

Use descriptive link text. Avoid labels such as “click here.” Check relative links after moving or renaming files.

## Numbers, dates, and time

- Use numerals for measurements and version numbers.
- Use ISO-style dates in technical examples: `YYYY-MM-DD`.
- Include a time zone when a timestamp could be ambiguous.
- Identify sample values as illustrative.

## Product claims and assumptions

Do not present an assumption as verified product behaviour. Mark simulated behaviour as illustrative. For a real product, verify statements about security, privacy, availability, integrations, data retention, and compliance with the responsible product owner.

## Review checklist

- [ ] Audience and purpose are clear.
- [ ] Procedure prerequisites are stated.
- [ ] Steps are in the correct sequence.
- [ ] Expected results are included where useful.
- [ ] UI labels match the glossary.
- [ ] Links resolve.
- [ ] Examples contain no real customer data or secrets.
- [ ] Product claims are verified or explicitly labelled as assumptions.
- [ ] Grammar, spelling, and formatting are consistent.
